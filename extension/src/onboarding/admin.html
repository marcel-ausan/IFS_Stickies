Administrator setup

Fifteen minutes, once per environment.

Two configuration packages — in this order, with a publish between them — and one permission set to update. No PL/SQL, no scheduled job, no integration, and no data leaves this environment.

↓ 1. Entity package ↓ 2. Event package

What to do

Navigator wording moves between IFS releases, so page names below are a guide rather than an exact path.

1

Import the entity package

IFS-STICKY-NOTES-LU.zip — the first download button above.

  • Open Application Configuration Packages in Solution Manager.
  • Use Import Configuration → the import package assistant.
  • Upload the file, review the items, apply.

2

Publish the custom logical unit

Publish CStickyNotes. This is what actually creates the table, its columns and the projection — importing only defines them.

Do not skip ahead to step 3. The event package refers to the entity’s columns — CF$_NOTIFYTO, CF$_NOTIFYSUBJECT, CF$_NOTIFYBODY — and those do not exist until this publish has run.

Importing the event first fails with Field [IMPORT_ID] is mandatory for Application Configuration Item Import, which is misleading: IMPORT_ID is generated server-side, so a null one means the import session was never created. Nothing is wrong with the file.

3

Import the event package

IFS-STICKY-NOTE-EVENT.zip — the second download button above. Same import assistant. It brings C_STICKY_NOTE_NOTIFY and its e-mail action, which are what send the @-mention notifications.

Skip this package entirely and everything else still works — notes save and mentions are recorded, but nobody is e-mailed.

Then set a mail sender that exists here. The event action ships with $SENDER = EDI_MAIL_SENDER, which is simply what the source environment used. It is not a universal value and very likely does not exist in yours.

Open the imported event action C_STICKY_NOTE_NOTIFY, find $SENDER in its action parameters, and set it to a mail sender this environment actually has configured.

Get this wrong and everything else still looks fine — notes save, mentions are recorded, the event fires — but no e-mail ever arrives, and nothing in the extension can tell you why.

4

Grant the projection

Add CustomProjectionCStickyNotes to the basic permission set that every user already has — the one assigned to all employees by default. Users need read and write.

Please don’t put this in a role-specific permission set. Sticky notes are a general-purpose tool like attachments: anyone who can open a record should be able to leave one. A partial grant means the feature silently works for some colleagues and not others, and the person who cannot save a note has no way to tell why.

Mentioning people also reads the standard person list, which essentially every user already has.

5

Add the page to the Navigator

The entity package brings an Aurena page group — StickyNotesList and StickyNotesPage — for browsing notes inside IFS. Importing it does not put it in the menu.

  • Open Navigator Designer (saved entries live under Navigator Configurations).
  • Add an entry pointing at the StickyNotes page group.
  • Publish the navigator configuration.

Optional — the extension itself doesn’t use this page; notes appear on record pages either way. It is for anyone who wants to review notes across records.

6

Verify

Ask one user to install the extension, enable it on this environment, and press Check IFS setup in the extension popup. It reports read and write separately:

  • Not found — the entity package did not import, or the LU was never published; revisit steps 1 and 2.
  • Read but not write — the permission set in step 4 is missing the grant.
  • Both work — the notes half is done.

The probe does not test e-mail, so finish by having that user @-mention somebody and press ✉ Notify. If no mail arrives while everything else works, the sender in step 3 is the first thing to check.

How the e-mail fires

Reference, beyond the sender in step 1. Worth reading before changing the event, because it is subtler than it looks.

i

The event C_STICKY_NOTE_NOTIFY is AFTER-MODIFY only, with MODIFIED_ATTRIBUTES = CF$_NOTIFYTO. It fires only when Cf_Notifyto changes — which is why typing in a note, saved every few hundred milliseconds, doesn’t e-mail anybody.

The action adds the condition CF$_NOTIFYTO != null and sends:

$TO      = &NEW:CF$_NOTIFYTO
$SUBJECT = &NEW:CF$_NOTIFYSUBJECT
$MESSAGE = &NEW:CF$_NOTIFYBODY
$SENDER  = EDI_MAIL_SENDER   <-- change this (step 1)

The extension composes the subject and body, including the deep link back to the record, so wording changes never require touching IFS.

  • Cf_Notifytrigger is written by the extension but not used by this event. It carries a fresh timestamp per send — a ready-made hook if you ever want the event keyed on something that always changes.
  • Because the event keys on Cf_Notifyto changing, two consecutive sends with an identical recipient list wouldn’t fire. The extension prevents that from the other side — Cf_Notifiedto accumulates everyone already told. The two are complementary; don’t remove one because the other exists.
  • The body is HTML. If recipients see literal <p> tags, this environment sends the action as plain text — say so, and the extension will emit plain text instead.
